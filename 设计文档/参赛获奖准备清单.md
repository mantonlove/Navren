- 题目为“银行 AI 智能体”，至少覆盖六个方向中的三个，鼓励全覆盖。所列子功能是典型示例，不应直接理解为必须完成全部子功能。[赛题](https://fintechathon.g-ican.com/)
- 需支持自然语言意图、任务拆解及执行，落实分级权限、安全机制、审计、失败处理和人工接管等技术要求。[赛题解析](https://fintechathon.g-ican.com/)
- 任务完成占 40%，安全合规占 30%，创新及交互占 30%。线上评审选十队进入决赛，后续还有现场黑客松、演示与答辩。[国内规则](https://fintechathon.g-ican.com/#/rule)
- 国内 AI 报名截至 11 月 1 日，作品截至 11 月 2 日。必交技术文档、答辩 PPT（不超过十分钟）、源代码及部署／测试材料、安全自评；五分钟以内演示视频在国内规则中为可选，建议制作。[提交规则](https://fintechathon.g-ican.com/#/rule)

## 2. 轻舟应形成的主线

定位建议：围绕用户账户，从收支分析、周期扣费识别到可支配资金判断，再到风险匹配的理财选择和经授权的业务执行。

将账单分析、理财操作、订阅／代扣管理作为三个核心场景，卡片管理作为第四个扩展场景。用户已选择四个方向，本建议保留四项规划，只对交付深度排优先级。

不要用流水收支结余替代银行可用余额，不把建议方案写成实际持仓。来源、金额、授权和最终状态在跨场景任务中保持一致。

## 3. 业务完成标准

| 方向 | 建议达到的完成度 | 评委可检查的证据 |
|---|---|---|
| 账单分析 | 导入与原子校验、准确收支分类、月报、异常提示；能追问并查看对应流水 | 分类与总额对账；退款／转账口径明确；每项异常有具体记录和规则依据 |
| 理财操作 | 风险画像、产品比较、风险／期限／流动性／起购要求匹配；后续接上授权后的申购或赎回流程 | 推荐和排除理由、产品数据来源；订单提交与最终状态分开；失败未伪报成功 |
| 订阅／代扣 | 从流水识别疑似周期扣费、用户确认、预计日期提示；后续明确银行侧或商户侧可执行的管理能力 | 候选关联流水；本地确认、银行拦截、商户取消分别显示状态，不能混为一谈 |
| 卡片管理 | 优先卡片查询、消费限额及交易开关，后续再考虑新卡／授信／挂失 | 操作对象、金额或规则、授权记录及操作前后状态；未接入能力不显示执行成功 |

第一场答疑已明确允许自建模拟数据和接口，轻舟可据此选择自建模拟业务服务。官方尚未给出统一模拟接口规范、逐项验收标准及模拟强验证细则；后续邮件如有更具体要求再调整。第三方海外沙箱不是当前交付依赖。本阶段完成本地标记不等于完成模拟代扣关闭，更不等于完成真实银行扣款取消。

### 自建模拟业务服务应做到的程度（轻舟内部设计）

- 使用独立模拟账户、余额、产品、持仓和代扣协议，页面清楚标为模拟环境；与用户导入流水隔离。
- 理财闭环至少支持：风险及期限匹配 → 比较产品 → 形成确定订单 → 用户授权及模拟强验证 → 执行 → 查订单终态、余额与持仓。禁止通过聊天回复或前端提示冒充执行。
- 订阅闭环至少支持：周期扣费证据 → 用户确认管理对象 → 查询模拟代扣协议 → 明确确认 → 关闭协议 → 再查询协议状态。银行侧扣款规则与商户合同状态分别记录。
- 所有模拟写操作保存后端状态和回执；遵守幂等、金额约束、操作归属、授权有效期与审计，允许注入超时、失败和结果未知等故障。
- 模拟结果同样要真实反映这个环境中的执行状态。计划赎回不得立即变成到账现金；无法即时完成的动作显示相应待处理状态，或者明确限定首版支持的模拟产品规则。

这些是对“完整功能流程”的实施建议，不是组委会发布的接口规范。模拟强验证用于证明权限机制，不能描述为真实银行身份验证。

## 4. 应演示的三类完整任务

建议将正常任务、安全拦截、失败恢复都放进展示，而非只展示若干互不相关的页面。

1. 收支诊断：分析指定月份账单 → 查看支出分类 → 解释异常提示 → 查看周期扣费及证据 → 用户确认候选。证明查询事实和计算准确。
2. 财富管理：在已知且注明来源的余额条件下，预留生活费和近期支出 → 获取用户风险／期限要求 → 比较候选产品 → 用户选择 → 分级授权 → 调用选定业务环境 → 查询最终状态及持仓。证明建议可以推进为经授权的行动。接入未完成时必须明确展示为待接入。
3. 异常与恢复：故意缺少金额／对象、临时改变数据、重复确认或让工具超时 → Agent 追问、拒绝旧确认、避免重复执行、查询状态或交给人工。证明复杂任务发生问题时仍有可靠结果。

跨场景衔接应体现实际依赖，例如余额未核实就不生成可执行订单、授权失败就不继续后续动作。历史账单报告只说明其数据期间，不能直接当成当前资产快照。

## 5. 安全完成标准

官方分级包括纯查询自动执行、小额转账等明确确认、大额转账及理财申购等强验证；确认和多因子认证必须与具体操作绑定。[完整赛题](https://fintechathon.g-ican.com/)

轻舟的内部验收重点：

- 模型负责理解与规划；后端决定动作是否允许、权限级别、验证是否有效和是否执行。
- 不能通过“忽略规则”“我是管理员”或账单备注里的指令跳过授权。
- 用户确认的是确定的对象、金额、规则及数据版本；改动后重新确认，确认凭证过期或被重复使用时正确处理。
- 同一订单或操作重试只执行一次；跨账户／跨会话不能读取或修改别人的数据。
- 区分待确认、执行中、成功、失败、取消及状态未知；只有业务回执核实后才报告成功。
- 连续失败或可疑行为按明确规则锁定；中断、回退和人工接管保留完整状态及日志。
- 缺失数据、异常接口及模型失败都不编造余额、收益、订单或取消结果。

这些需要测试和现场演示支撑，不能只在安全报告中写原则。本地标记确认不是银行强验证；第二阶段需要为模拟红色业务设计独立验证步骤，并绑定确定的操作内容。

## 6. 创新与交互应如何证明

轻舟可以突出：同一财富管理任务下的个性化解释、必要追问、少跳转、多步骤处理，以及用户随时暂停和查看依据。

三种界面模式、语音和可视化可作为呈现方式，但应证明它们如何降低操作负担。例如老人是否更容易确认金额和风险，普通用户是否能更快找到异常交易，不熟悉金融术语的用户是否能理解产品差异。以上效果需要测试，不预先宣称成立。

比较同一任务在传统页面路径与轻舟中的完成步骤、耗时和错误情况；没有真实比较数据就只描述设计目标。无需为“创新”提前引入新框架或增加多智能体数量。

## 7. 必须准备的验证证据

提前固定常规、歧义、故障和攻击案例，保留预期结果与完整运行记录，避免只挑成功案例展示。分别记录：

- 任务成功率：先定义完成条件，成功应包含目标状态核查；未支持的任务单列。
- 金额／分类正确性：与独立计算或人工核对结果比较。
- 安全拦截结果：每条攻击的目标、实际结果、是否发生未授权变更。
- 重复提交与失败恢复：最终状态、是否重复产生业务影响、是否需要人工接管。
- 用户体验：完成时间、必要追问轮数、确认对象是否明确。

报告注明测试集大小、版本、环境、数据来源和已知限制。不能将有限测试中零次越权描述为系统绝对安全。内部历史自评分与本赛事评分是不同口径，不当作获奖依据。

## 8. 材料与路演

技术文档围绕真实架构、关键工具、数据来源、权限及状态设计、异常处理和验证结果组织。源代码提供可运行 README、依赖、示例数据、部署步骤、测试入口和 GitHub 地址。安全自评列出已实现控制、验证证据和已知风险。[材料要求](https://fintechathon.g-ican.com/#/rule)

建议十分钟路演：问题与用户需求一分钟 → 正常任务四分钟 → 安全及失败恢复两分钟 → 验证结果与架构两分钟 → 价值和边界一分钟。五分钟演示视频保留最能证明能力的完整任务与安全片段。该时间安排为内部建议。

结合第二场的交付经验，代码版本、测试证据、部署入口、材料及现场演示分别指定负责人；提前冻结提交版本，完成至少三轮完整答辩演练，邀请不了解项目的人检验前三十秒能否听懂用户、问题和方法。提前提交可运行版本再更新，具体提交时点仍按官网及报名后台。体验环境只开放独立模拟数据；不得直接公开本机导入账单数据库。

演示数据、模拟环境和真实账户证据明确标注；材料、视频及现场运行使用一致的版本。决赛准备可修改、可部署、能快速排错的系统，以应对现场黑客松和评委临时输入。
