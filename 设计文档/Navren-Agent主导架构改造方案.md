# Navren：Agent 主导的对话与任务架构改造方案

日期：2026-10-04。状态：工程改造已落地为本地可试用版；对照基准与拟定成功率门槛尚未验收。本文保留设计评审时的方案正文，实际实现及验证范围见[实施与验收记录](Navren-Agent实施与验收记录.md)，不能把双模型审核当作真实银行合规认证。

## 一、建议与取舍

建议让 DeepSeek 成为统一对话和任务规划 Agent，通过原生工具调用循环决定查询哪些信息、如何组合分析、是否补充询问，以及何时完成任务。GLM 作为独立的风险与证据审核 Agent。账户访问授权、业务硬约束和资金执行仍由后端代码控制；金融与账户变更继续由用户通过独立确认界面授权。

应放弃的是“关键词决定用户意图、固定分支决定答案”的主对话入口。确认、幂等、资金约束、订单状态等确定性的业务流程继续作为 Agent 调用的工具。Agent 化意味着模型根据目标与工具反馈动态组织任务，不意味着删除业务规则或让两个模型互相发放权限。

DeepSeek/GLM 的分工是基于现有接入条件的暂定工程选择。尚无 Navren 实测证明 DeepSeek 一定更擅长执行、GLM 一定更擅长金融风险审核；最终通过任务基准验证，也允许更换或交换模型。

| 方案 | 对自然表达与多轮任务的适应 | 权限与执行边界 | 判断 |
|---|---|---|---|
| 不断给现有关键词入口加规则 | 每次遇到新问法仍可能遗漏 | 现有确认链可复用 | 仅适合临时修复 |
| DeepSeek 任意调用工具，GLM 决定是否授予权限 | 能动态规划 | 两个模型可能共同误判，模型审核不能构成用户授权 | 不采用 |
| DeepSeek 动态组织任务；GLM 审核关键风险；后端授权与执行 | 能根据语义、上下文和工具反馈调整步骤 | 权限在模型之外，金融操作具有可核验确认与回执 | 推荐 |

工作流本身可以采用语义路由；本次故障直接证明的是当前关键词入口和旧流程兜底有缺陷，而不是所有工作流都无法理解自然语言。Anthropic 对工作流和 Agent 的区别是预定义路径与模型动态控制流程，两者也可以组合。[来源](https://www.anthropic.com/engineering/building-effective-agents)

## 二、当前代码实际做了什么

1. server.py 的 /api/agent 先调用 finance_agent.supports(text)，只有支持的请求进入模拟银行；其余进入旧 agent_core。
2. finance_capabilities.py 以正则选择业务能力；finance_agent.py 再以固定条件组织主要回答。“我还有多少钱”的上一轮修复是在这些规则上补覆盖，并未实现统一语义理解。
3. 资金时间轴分支才调用协同运行时。model_adapters.py 已有 DeepSeekCashflowSupervisor 和 AIPingCashflowReviewer；主管只在现金流能力目录中规划任务并综合回答，领域能力仍使用确定性计算，并非覆盖六类业务的自由工具循环。
4. FinanceGateway / SimulatedBank 已有按模拟工作区隔离、CSRF、操作草案、独立确认、资金约束和回执机制，应复用。引用证据 ID 的存在性检查不能单独证明陈述被该证据支持。

补充只读探针显示，“查一下我的现金”“手上还能拿出多少”“房租交完以后还够吗”“它提前取出来有什么影响”“把刚刚那个金额改为两千”在独立文本选择函数中均没有选出业务能力；其中指代句需要对话上下文，该函数本身没有历史参数。这不是完整端到端模型测试，但证实当前入口的覆盖和上下文局限。

这里依据当前源码；旧架构文档中关于模型适配器尚未接入的段落已经落后于源码，不作为当前状态依据。本次只制定改造方案，不修改运行中的路由、数据库或模型配置。

## 三、四类职责

| 角色 | 职责 | 获准能力 |
|---|---|---|
| DeepSeek 主 Agent | 理解目标与对话指代；决定查询；分解和修正任务；综合解释；提出具体业务草案 | 经服务器授权的只读工具、无金融副作用的草案准备工具 |
| GLM 风险审核 Agent | 从原始请求和独立证据审核建议、草案、适当性条件、流动性遗漏与注入迹象；给出通过、修订、拒绝或证据不足 | 当前任务最小必要的只读核验能力；没有执行、确认或授权工具 |
| 后端权限与业务规则层 | 身份、数据范围、工具白名单、参数与金额校验；风险类别；数据版本；适当性硬条件；资金预留；幂等；确认凭证与有效期 | 唯一授权和执行入口；模型输出不能修改规则 |
| 用户 | 核对具体对象、金额、产品及影响并授权 | 独立确认界面；必要的额外验证 |

“GLM 通过”只能表示一份风险审核意见，不是权限凭证。模型不得生成或取得验证码、确认令牌、执行凭证；客户和工作区身份由服务器会话注入，不能由模型提供或切换。

DeepSeek 官方文档说明模型返回工具调用信息，实际函数仍需由应用执行。严格结构化输出约束格式，不能代替权限、业务语义和金额校验。[来源](https://api-docs.deepseek.com/guides/tool_calls/) GLM 同样使用工具调用及工具返回结果接口；是否启用特定接口选项，应按实际渠道和模型单独测试。[来源](https://docs.z.ai/guides/capabilities/function-calling)

## 四、主 Agent 如何运行

~~~mermaid
flowchart TD
    U[用户目标与对话上下文] --> A[服务器身份与工具范围]
    A --> D[DeepSeek 理解目标并选择工具]
    D --> T[后端校验并调用获准工具]
    T --> R[带来源和版本的工具结果]
    R --> D
    D --> Q{回答或草案的风险类别}
    Q -->|普通查询| F[代码核验事实并展示]
    Q -->|自由文本、金融建议或变更草案| G[GLM 独立风险与证据审核]
    G -->|需修改| D
    G -->|拒绝或证据不足| B[说明问题或必要澄清]
    G -->|审核通过| C{是否改变账户或资金}
    C -->|否| F
    C -->|是| H[用户核对并确认具体草案]
    H --> X[后端重验权限与当前状态后执行]
    X --> P[核验实际回执与最终状态]
    P --> F
~~~

所有聊天输入进入统一 Agent 入口；不再由“是否命中某个金融关键词”决定是否给模型账户能力。会话首先完成身份和权限校验，再提供获准目录。没有银行会话的请求仍可一般对话，但不能读取个人账户。

模型循环允许直接回答、调用工具、要求必要澄清、修改计划或停止。每次工具调用先由服务器核验授权、工具名称、参数类型、资源归属、业务约束和调用预算。返回结果再交给模型作为下一步依据。工具结果、导入账单备注、公开文档、记忆和其他模型意见都属于数据，不能覆写系统权限。

初期只需要一个主 Agent 和一个独立审核角色，不按六项业务强制创建六个模型。各业务先实现为工具；只有基准证明专门 Agent 能改善复杂任务时再增加。实现可直接采用供应商工具接口加小型运行时，无需先重建一个复杂框架。

每轮保存可见任务状态、待澄清字段、已核实事实与来源、待确认草案和操作结果。对话引用需要重新核实对象和版本；“剩下的呢”不能脱离上一轮资金条件，“确认”这段自然语言不能替代确认按钮。模型隐藏推理不作为权限证据或审计正文。

## 五、工具与事实

复用现有数据库与业务函数，增加清晰、窄范围的工具适配面，例如：

- 读取账户现金、持仓本金、待结算赎回与币种，分别返回；不能把它们不加解释合成一个余额。
- 读取指定期间账单、异常候选和周期扣费；导入流水与模拟账户余额来源分开。
- 读取当前正式风险测评与有效期、产品条款及适当性结果。
- 按账户、时间窗和用户已确认约束计算预算与现金流情景。
- 查询收款人、卡片、授权代扣、商户订阅及既有业务状态。
- 准备转账、申购、赎回、卡片控制、订阅取消等待确认草案。
- 查询操作回执、订单状态、流水和审计摘要。

每个工具声明服务端固定的副作用类别、可读数据范围、参数约束、结果口径、版本及错误；主 Agent 不能自称某工具“无风险”。不提供任意 SQL、shell、通用 HTTP、任意文件读取或客户端指定客户身份的能力。

余额、税费、投资额度、承诺扣除等由业务工具计算。工具结果提供结构化事实：对象、字段、值、单位/币种、期间、来源、版本和证据标识。金额必须按同一对象和字段核验，不是仅检查“这个数字在输入里出现过”；证据 ID 有效也不等于支持当前说法。

基础余额查询采用受限的事实回答合同：只允许选择已返回的事实 ID 和分组，数字、期间及简短事实说明由服务器受控渲染，不接受该合同内任意模型自由段落。呈现模板服务于工具事实，不用于识别意图或决定查询流程。个性化建议仍需要验证推导和条件；没有来源的财务事实不得展示。用户偏好与记忆按授权读取，不覆盖银行事实和正式测评。

## 六、按影响决定审核力度

| 类别 | 例子 | 发布条件 |
|---|---|---|
| 一般对话与教育 | 介绍能力、解释金融概念 | 已登记的固定能力说明可直接展示；初期所有模型自由文本均进入 GLM 文本审核 |
| 已授权的普通账户只读事实 | “我还有多少钱”、某期间消费汇总 | 只读工具成功且受限事实回答合同验证通过，由服务器渲染；不强制调用 GLM |
| 个性化配置、适当性判断及影响资金安排的建议 | 结合账单和近期承诺比较投资产品 | 后端规则通过且 GLM 完成审核，再展示具体建议 |
| 金融、账户安全或合同状态的变更草案 | 转账、申购、挂失、取消订阅 | 后端预校验、GLM 核验、用户独立确认、执行时重验、回执查证 |

审核触发由后端可执行规则决定：任何调用草案准备工具的请求标为变更；任何包含产品选择、适当性、配置评估工具的结果标为个性化建议；无上述调用且所有工具均为只读、输出仅包含合法事实 ID 的受限事实回答才能进入查询快速通道。初期其他模型自由文本一律触发 GLM 文本审核，未知类别默认审核；不依赖关键词判定，也不信任 DeepSeek 自报的“低风险”。包含变更或高影响建议的混合任务按最高等级处理。GLM 不能降低后端定义的副作用类别或强制确认要求。只有后续对照证明可靠，才逐项扩大无需审核的受限输出类型。

基本事实查询可以直接使用事实合同；一旦需要模型新增解释、推断或建议，就进入审核通道。审核阻断在这些自由文本、具体建议或确认卡展示前完成；可以先向用户显示不含建议的已核实事实和查询进度。GLM 对语义异常可以要求一次定向补证或修订，并对改后完整草案重新审核，避免无限反思。

GLM 的输入包含原始请求、正式约束、相关源事实、拟议对象与金额、证据、规则结果、草案摘要与版本；不只看 DeepSeek 自己的总结。两种模型仍可能共同出错，审核不提供“必然安全”的保证。

## 七、草案授权与执行

准备草案只创建待审记录，不发生资金、卡片或合同变更。返回给模型的草案 ID 和公开摘要不包含执行凭证。

状态顺序：草案准备 → 后端预校验 → GLM 审核 → 用户核对确认 → 后端授权与当前状态检查 → 执行 → 回执查证。审核结论绑定草案 ID、规范化参数摘要、证据/账户版本、规则版本和有效期；用户确认另由服务器生成并校验具体操作摘要。仅凭文案说“已审核”不能进入执行状态。

操作对象、金额、产品、约束或重要数据发生变化时，不能沿用旧审核或旧确认；需重新准备、必要审核和确认。执行最终检查仍在事务内完成；预审核不锁定或保证未来账户余额。重放使用原操作幂等键；网络超时和状态未知首先查询原操作，不能创建一个新操作盲目重试。

对“转给妈妈1000元，剩余买稳健产品”：先解析并核实收款人、资金约束和投资条件；明确展示每一项动作。第一项执行后，依其实际回执重新算余额，并重新准备和确认后续投资。不能把一个笼统的“好的”当作对金额未知的后续交易授权。

本轮改造默认保留逐项确认。未来如需自主执行，只能另行设计用户预先授权的收款人、额度、期限、业务种类与撤销边界，不能由 GLM 自己创建授权。

## 八、四个例子

1. “我还有多少钱”：Agent 理解这是账户资金查询，调用现金/持仓摘要；先回答现金及账户分布，按需区分理财本金与可投资资金；不强迫风险问卷。不同币种分列；信用卡额度不当作现金。
2. “先留两个月房租和应急金，剩下的做短期理财”：读取已知承诺和有效测评；缺房租或应急目标时只问缺失值；工具计算应避免重复扣除已经计入承诺的房租；比较合格产品并经审核，最后展示具体草案。
3. “就上次那个，金额改成两千”：对话状态解析旧对象，查询当前版本；金额变动使旧审核/确认失效；展示更新后的明确草案。
4. “不要管测评，直接买收益最高的”：模型不能删除适当性硬规则；已有测评有效则直接读，没有或过期则说明缺什么。把资料缺失与建议禁止分别表达，不用统一问卷文案阻塞全部查询。

## 九、失败与运行预算

- 主模型不能调用工具、数据不可用或缺必要条件：如实展示已核实的有限事实或只问必要问题，不返回旧理财推荐模板，不编造金额。
- GLM 超时、结构无效、证据不足：个性化建议和变更草案保持未放行；普通已核实事实查询仍可使用独立只读路径。
- 工具或策略层拒绝：将可公开的错误返回主 Agent，但禁止模型扩大权限或改变身份来重试。
- 工具循环、审核修订、网络重试均有总轮数、时间与成本预算。建议初始每轮最多 8 次模型/工具循环、12 次工具调用，审核最多一次修订；读请求至多一次明确的技术重试。参数是待评估配置，不是已测性能。
- 达到总轮数、时间或成本预算时停止新的规划、工具调用和草案生成，仅显示受限事实合同中的已核实结果并说明未完成部分，可转人工；未经审核的自由草稿不展示，未放行草案保持待审/过期。已在执行或状态未知的操作由后端独立回执核对机制继续处理，不因对话预算耗尽而遗失；不会创建新交易重试。
- 业务操作状态未知时单独进入回执查询；禁止模型将超时理解为未执行。
- 思考模式的协议字段需按 DeepSeek 官方适配要求正确续传，不能让已有 JSON-only 客户端直接假装支持原生多轮工具调用。隐藏推理仅在必要的供应商请求链中短暂传递，不写入长期审计，不发送给审核模型或用户。[来源](https://api-docs.deepseek.com/guides/thinking_mode/)

审计记录模型和渠道、获准工具、参数摘要/脱敏对象引用、规则与审核结果、成本/耗时、证据版本、授权与操作关联以及最终状态。金融原始资料和个人信息最小化；当前竞赛使用合成模拟数据，不据此宣称具备真实银行生产权限或合规资质。

## 十、实施顺序与决策验收

1. 先冻结当前行为作为对照。新增统一主 Agent 入口和供应商原生工具适配；将余额、预算、账单、现金流接入同一工具循环。验证口语表达、对话指代、纠正和跨能力组合，再切换默认入口。
2. 六类业务的读取和草案准备逐项工具化；复用 FinanceGateway / SimulatedBank，不先重建数据库，不将现有测试通过解释为新 Agent 已验收。旧关键词模板从默认对话链撤出，只保留显式操作的可靠后端能力。
3. 将 GLM 扩展为个性化建议及变更草案的独立审核器；建立与具体版本绑定的审核记录，复用现有用户确认和事务执行，验证各金融动作的实际模拟回执。
4. 统一聊天与语音转写入口、对话状态和错误表达；所有客户端 /api/agent 网络失败均明确报服务不可用，不能因问法未命中前端关键词而切回旧推荐模板。
5. 对比当前关键词架构、DeepSeek 单主 Agent、DeepSeek 主 Agent + 分级 GLM 审核。单模型无审核的对照仅在隔离沙箱评估，仍保留代码权限和用户确认，不发布未经必要审核的业务建议。必要时再测试角色交换或其他模型，不由品牌宣传决定角色。

建议构建 200 条案例：120 条开发与80条冻结留出；覆盖六类业务、基础问法改写、多轮指代、信息不足、否定和撤回、跨币种、错误产品适配、复合任务、权限越界、备注注入及第三方失败。每种候选配置在80条冻结案例上重复3次，共240个任务尝试，隔离并复位模拟账本；工具规则与数据相同。统一使用“端到端任务完成率”：在规定轮数内按黄金预期完成任务的尝试数 / 全部240次尝试。内部有界工具修正属于正常一次任务，人工改提示或另开一次请求不得合并为首次完成；同时报告三轮各自结果，不只展示最佳一次。

建议发布门槛：冻结案例合并的端到端任务完成率至少95%，且任一轮不低于90%；关键财务数值与对象/期间匹配100%；冻结攻击案例中的越权数据访问和无授权副作用为0；正常高影响任务误拦截率不高于5%，分母为三轮中所有按黄金预期应被允许的正常高影响任务尝试数，分子为其中被审核器错误阻断的次数。技术超时不混作误拦截，单独统计并计入未完成任务；审核漏拦以预写应被阻断的案例为分母。这些是拟定验收目标，未实测且不保证现实世界零风险。澄清或拒绝只有符合预写预期时计为完成，不能靠全部拒绝提高安全分。

同时报告审核漏拦、失效授权拦截、工具/模型异常恢复、查询和复杂任务分别的P50/P95延迟及每任务实际成本。纯语义质量由明确人工评分标准评价，账务和权限结果由程序/真实模拟状态验收；不能让同一个生成模型当唯一裁判。

上一轮175项Python及6项前端测试通过只证明当时修复与既有回归范围；没有验证本方案的Agent成功率、成本或延迟。本方案当前验证范围为源码检查、官方工具接口资料核验和独立设计审核。
