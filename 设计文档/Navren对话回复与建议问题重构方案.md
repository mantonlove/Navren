# Navren 对话回复与建议问题重构方案

日期：2026-10-06。状态：用户追加要求“还有一个问题跟着一起改”，按本方案增量落实回复重构、日历小卡与图文交互；具体实现及验收待各窗口交付。依据：用户三张截图及当前正式源码的只读检查；规划本轮只补充合同和分发，不改业务源码、不重启服务。

目标：让用户先读到回答，再看关键数字，最后按需查看细节并继续提问。改动覆盖 Agent 表达、金融展示合同、前端信息层级、消息生命周期及集成验收。继续沿用既有主模型和审核模型，不为润色增加一次付费模型调用。

本轮对应五项用户反馈：缩短单条默认回复、让语言自然口语化、用数据呈现代替括号点评、收紧只有按钮的空卡片、恢复并重设计建议问题。

## 2. 回复表达：结论、结果、下一步

普通查询：一句回答，必要时一个小结果。分析任务：一两句结论、一个主要结果面板、最多两条判断。比较任务：默认比较影响选择的2–3个维度，其他条件展开。准备操作：突出对象、金额和“待本人确认，尚未执行”，不再叠加通用账户大卡。复杂长报告只有在用户明确要求时完整展开。

第一屏不是强制截断整条回答。默认阅读层控制重复信息，完整依据按需打开；金额对象、期间、来源范围、关键缺项、假设、风险和操作状态必须保留。用户问“为什么”、要求逐笔、完整推导或深度研究时，允许长答复。

中文表达建议：

- 普通查询正文约40–100字；常规分析约100–220字，最多3个短段落。这是写作目标，不是机械截字规则；英文按句子和阅读长度设独立目标。
- 直接回答问题，少用“总览”“几点说明”“综合来看”“值得关注”等固定套话；不要写开场寒暄、重复问题或总结同一结论。
- 自然表达不等于随意评价。例如“最大头，占一半以上”改为“电子产品是最大的支出项”，占比放在数据行；没有可靠判断标准不称“明显偏高”“缓冲很薄”。
- 只有实际取得并核验资料才说“我查到”；资料不足具体说缺什么，不把技术错误码交给用户。根据截图可说“算上退款，这份账单里支出比收入多1,986元。电子产品花得最多，可以先看看是哪几笔。”这不表示当前账户欠款或透支。
- 不重复朗读完整分类和长免责声明。语音保留同一简短结论及重要条件；图表明细按需朗读，不能另行生成未经核验的金融摘要。

## 3. 截图中的账单：默认展示样例

以下使用截图原数字，是界面样例，不作为实时账户查询结果。

```text
算上退款，这份账单里支出比收入多1,986元。
电子产品花得最多，可以先看看是哪几笔。

9月账单                          9月1–29日 · 29笔
收支差额 −1,986元
收入 6,500元    消费 8,526元    退款 40元

电子产品   ━━━━━━━━━━━━          4,744元
住房       ━━━━━                 1,800元
购物       ━━━                   1,058元
其余5类                             924元  ›

来自本次导入流水，收支差额不代表账户余额。
查看29笔明细 ›                口径与来源 ›
                                  朗读  收藏

看看电子产品明细 ↗     找找固定开销 ↗     对比上月 ↗
```

分类默认前三项加其余合并；点击分类进入同一报告的逐笔详情，点击“其余5类”展开其余分类。数字右对齐，类别左对齐，单位一致；日期和覆盖用短标签，不写成长段。

条形长度来自后端确认的同范围金额关系；百分比须由后端在明确分母/期间/类别/退款口径后计算并验证，不能由模型或前端另算。若相应比率合同尚未具备，先展示金额和条形，不凭文案添加“56%”。缺上月记录时不提供“对比上月”；根据实际数据换成可用问题，不强凑三项。

“支出最大项”是一项排序事实；“消费过高”是需要预算、历史和目标支持的判断。排名不用红色警报。蓝色用于中性强调，收入/支出用文字和符号区分；投资盈亏沿用既有颜色约定，不把支出、赤字一概涂成投资亏损。

重要误读边界直接露出一行；计算细节、完整出处、退款与转账分类、完整风险说明进入“口径与来源”。问号只解释名词，不承担隐藏关键条件的职责。

## 4. 消息与卡片布局

| 对象 | 设计规则 |
|---|---|
| 普通文字 | 保留左侧 Navren 身份，弱化大外框；文字按内容高度布局。桌面阅读列约720–760px，不将小组件强行拉满 |
| 数据结果 | 一份回答默认一个主面板，12–16px内边距、约12px分区间距；减少卡片套卡片；关键金额突出，其余用紧凑行 |
| 详细解释 | “查看明细”“口径与来源”局部展开或打开详情侧栏/全屏页，保留返回位置；不在气泡中再创建内部滚动条 |
| 导航与工具 | 放在内容后的单行：左侧必要的查看入口，右侧朗读、收藏等轻工具；图标有可访问名称及状态，收藏后保持可见 |
| 只有动作 | 使用紧凑动作行或简短状态条，不生成全宽结果卡；没有正文、结果和有效动作时不保留空气泡 |
| 执行确认 | 继续保留明确的业务确认组件和独立状态；不能为了省空间混成普通建议问题，也不隐藏金额、对象、约束 |
| 窄屏与关怀版 | 数据两列或单列、文字正常换行；移动触区至少44px，关怀版至少48px。桌面轻工具视觉约32–36px；不靠缩字号压密度 |

取消工具绝对定位与固定54px底部预留，让内容、工具行、建议问题按正常文档流排布。普通正文行高约1.6–1.7，段间约8px。数字使用等宽数字特性，长金额和英文标签能够换行而不互相覆盖。

在普通字号1440×900/1280×800视口中，常规账单回复的默认文字、结果面板、工具和建议应可在一个聊天可视区内阅读，主要内容目标约320–420px；遇到大字号和重要条件允许增高，不用裁切或省略关键内容强行达标。用户正在看历史时不抢滚动，只提示新回复；展开详情后保持当前阅读位置。

## 5. 建议问题：少量、具体、可继续

建议问题是对话的下一步，放在最后一条有效主回复下方，脱离数据卡的边框但与正文对齐。默认2个，确有价值时3个；通常每项8–16个汉字，不使用三张大推荐卡。样式为低对比细边/浅底的紧凑问题签，间隔8px，右侧一个小箭头。桌面一行，窄屏自然换行，支持键盘焦点与触控，不靠横向滑动隐藏问题。

选择规则：围绕当前对象继续深挖、比较已具备的数据或补充会改变结论的缺项。排除刚回答过、依赖缺失资料、无工具支持、与问题无关或包含无证据结论的建议。查询支出不能每次跳到“风险测评”“买理财”“最近市场怎么样”；问题不包含新的未经绑定金额。

先做兼容修复：统一规范化入口，支持现有字符串与对象，所有渲染/点击/历史恢复路径共用。第一步沿用前端已认识的label/text/type="send_message"结构，字符串按安全问答问题转换；空标签、空发送内容和未知类型拒绝，不推测交易权限。随后为稳定结构增补schema_version、id、intent、context_ref、availability；现有text保留为完整发送问题，不同时引入含义重复的prompt。服务器保存与message/workspace/request及快照的绑定。对外模型、浏览器与受信服务器各用其受限投影，不把私有标识拼进公开检索。

answer_reviewed 在同一次终结中提出候选；answer_facts 由工具能力与已查询对象提供受控模板候选。服务器筛选、去重及核验可用性后返回，不增加一次“建议问题模型”调用。事实、缺项和操作状态已经确定时，模板只能提问，不替用户判断或补金融事实。没有合适问题时可只提供一个补充资料入口，不能为凑数输出误导问题。

首版建议语义只支持 ask 和 open_view，兼容层将ask映射为现有send_message渲染类型，不让模型自由选择前端特权动作。点击问答建议发送其完整提问并附受控上下文，默认查询/分析；导航建议打开真实对象。建议问题不是确认按钮，不接受/执行交易或服务申请，不由前端文字匹配生成交易权限。用户后续另行明确提出操作时，沿用原准备、审核和本人确认链。

建议区属于当前工作区/会话最后一条已完成主回复，不由最后一个DOM节点决定。发送新问题时暂时隐藏旧建议，新回复完成后替换；系统通知、录音和播放不抢归属。失败提供明确重试或仍安全的补资料建议。

历史保存结构化消息和建议描述，保留消息ID、范围和语言；刷新重建最后一组有效建议。历史建议点击时重新检查对象、账户和版本，以“这份历史账单”还是“当前账户”为依据明确查询范围。旧确认卡及过期动作不恢复成可执行按钮。切账号取消旧异步请求、语音与建议，失效组件移除或变成明确状态条，不留空壳。动态文本、问题与展开详情同步中英切换，防止先中文后英文。

## 6. 输出合同与金融审核

先保持现有终结工具、amount_claims和紧凑来源协议，添加受控的展示投影，而不是让前端截断Markdown或审核后调用模型改写长文。

- Agent 直接生成最终短正文；金融关键判断和必要限制完整进入本次审核。初版保留现有text/claims/amount_claims/draft_ids/widget_ids/followups字段，不为简洁删除金融签名。
- 回复字数目标只针对用户正文，不下调原生4000输出上限来强迫缩短；该额度还承担工具参数和金额签名。省去长列表和重复解释，而非截断结构化参数。
- 结果面板从本轮已经发行并验证的指标/报告建立；Agent只选择指标和受控布局，不生成自由金额、百分比或任意HTML。Base生成与真实对象、期间、来源及版本绑定的presentation；UI只格式化和排版，不独立重算金融结果。
- presentation 明确schema_version、布局类型、所选指标/报告引用、重要状态及详情引用。数值来自受信指标快照；类别数量、排序和占比亦须有对应依据。收益率继续用ratio/value_decimal，不塞进金额字段。
- 所有用户可见的标题、正文、数据、标签、缺项、动作状态和问题候选形成同一确定性审核视图；同步更新 CloudDataBoundary 投影及敏感检查、review_packet、金额/事实校验、持久化和最终文字/语音守卫。不能只改输出schema却让GLM看不到新字段，也不能审核旧文字后展示改写稿。
- 前端点击展开只改变可见层级，不生成新事实；读取新明细和当前状态时另走身份/版本核验。收藏、HTML历史和缓存不绕过过期/撤回检查。
- 保留现有24条金额声明上限、同轮来源ref与metric绑定、完整/紧凑兼容、实际双模型预算及期限。每个实际展示的个人金额位置均须覆盖，正文与卡片重复相同金额不能凭同数豁免；超过上限减少默认展示项或将明细分组另行查询，不静默删声明。展示面板若需要另一种指标合同，单独版本化和验收，不静默放宽守卫或另开预算。

如果现有受控任务组件已能承载某种结果，应直接复用；只补展示层和缺失的数据投影，不另建一套指标注册表或答案协议。

## 7. 获准后的分工与顺序

实际派发前重新查询当前文件持有者。下表是职责，不能据此抢占RAG仍在接线的server/gateway/evidence文件。

| 会话 | 增量任务 |
|---|---|
| Agent构建 | 回复写作规则、按任务选择展示信息、短正文与完整证据共审、同轮建议候选；不额外加润色模型 |
| 基座 | 受控结果投影、事实回答建议、对象与版本绑定、历史消息合同；服务接线按当前owner完成 |
| UI | 文本/数据/动作层级、紧凑工具行、建议问题规范化与状态机、刷新/切账号/语言/语音恢复 |
| 金融方法与计算 | 仅在现有指标不足时补排序/分类占比等确定性口径，核验分母、退款、覆盖及独立预期；不重做已有方法 |
| RAG构建 | 资料引用与详情按已有合同提供；产品/市场回复保留真实出处和版本，配合当前接线交接 |
| 集成验收 | 真实后端→浏览器的端到端合同、金融内容完整性、用户阅读效果与全部状态回归 |

第一步：先修建议问题类型失配、事实路径缺失和历史恢复，去掉通用空气泡。第二步：用账单、资金安排、产品比较和日历四类结果试做新阅读层级，完成真实截图与中英/窄屏核对。第三步：冻结新展示合同，复验真实主模型＋GLM和最终守卫，再推广到其他任务。现有金融补丁与候选验收继续推进，本提案不能用来跳过原失败题或破坏冻结原件。

## 8. 验收要求

1. 用户能在默认回复中找到问题的答案、关键数字、范围和下一步。用5–8个典型问题做阅读核对，记录用户找答案的耗时和遗漏，目标在约5秒内定位关键信息；这是内部设计目标，不是已测结果。
2. 两张截图对应场景：账单不默认逐类复写全部明细；只有导航/收藏不产生高大卡片；重要条件没有因折叠消失。
3. 使用真实后端字符串、对象、空建议和非法结构分别测试，不只测试前端手写对象；查询事实、解释、失败、刷新、返回、语音和切账号后建议归属正确。
4. 一组金额、对象、期间、退款、未知覆盖、候选与操作状态负例同时覆盖短正文和结果面板；数值改错、同额错对象或过期版本不能因为卡片化而通过。
5. 实际原生主模型与GLM收到和核验同一最终内容，新展示字段不被隐私投影丢弃。模块通过、真实模型通过和浏览器实屏通过分别记录。
6. 1440×900、1280×800、375×812，中英、键盘、触控及放大字号检查无内容遮挡或按钮重叠。普通回复一个聊天可视区可读；大字号优先保证完整与可读，禁止气泡内二次滚动。
7. 不增加一次摘要/建议问题付费调用，不上调已有预算、不放宽本人确认边界。交付记录实际调用次数、Token、耗时、源码/合同/数据版本与失败原件。

用户已要求日历与上述问题“一起改”，由「规划」沿已确认现有会话路由增量分发，无需用户逐个转发。既有金融候选正在冻结验收，新的回复/图表合同在隔离候选中推进，不能修改原冻结原件或把本轮分发记作实现通过。

## 9. 消息内日历小卡与图表模板

### 9.1 复用与当前约束

截图的“按日查看事项”来自bank_ui.js:75–109的旧cashflow折叠列表。真正的CalendarUI已经支持日期格、收益状态、点击日期、查看事项及带引用提问；聊天统一任务结果与CalendarUI当前又是两个追加路径。将它们接入同一消息组件的正文插槽，保留短结论，直接展示日历或图表，不再把组件堆到完整长文尾部。

聊天组件使用独立紧凑样式，不把账户页完整工具栏搬进气泡；同时修正design.css后置七列规则覆盖单日/事项视图单列规则的问题。复用已有身份、失效、日期详情和事件编辑合同；不重造另一套日历数据库。

当前calendar_query和预算情景最多93天；cashflow最多365天，但提供未来日终推演，且只列有事件日期。多年历史不能从它推断，也不能让前端循环拼接93天快照当作统一审计过的时间序列。按月/年汇总应优先复用annual_statement等权威历史入口，由后端在同一版本快照生成新聚合序列；无完整收益边界或持有份额时，收益图明确不可计算。

### 9.2 按问题和跨度选择布局

| 用户想看什么 | 默认消息内展示 | 进一步操作 |
|---|---|---|
| 今天/某一天 | 单张日卡，日期、主指标、最多两项事项；重要状态直接显示 | 点事项看完整金额、状态、来源，继续针对该事项提问 |
| 一周/短期事项 | 逐日小卡，桌面一排七日；窄屏横向滑动并有明确翻页和当前范围 | 选日显示该日详情；无记录与数据未知分开 |
| 一个月的日程 | 紧凑七列月历，日期、类别点、事项数/已核验主值，不堆完整事项标题 | 选日后在月历下方显示一张详细日卡；月份切换保留来源与对象 |
| 一个月的每日收支/波动 | 按数据能力给分组日历或按周聚合柱图，保持同一期间 | 点击周进入逐日小卡；用户明确要求每日时按受控窗口分页 |
| 几个月/一年 | 按月柱图或有真实时间序列的折线图 | 点月份进入月历，再点日期，逐级钻取 |
| 几年/十年 | 按年柱图/折线＋关键转折的有依据注释，不展开数千天 | 点年份展开月图，点月份展开日历 |
| 钱花在哪/收入来源 | 前几类横向条形图；类别少且完整时可选环形图 | 点类别筛出相同范围的相关明细 |
| 理财盈亏/账户现金变化 | 收益柱图或现金/权益曲线，区分存量、期间损益、累计损益 | 点日期/区间读取相应产品、费用和交易依据 |

时间跨度只决定粒度，问题意图决定图型。问生日或缴费，不因为期间长就画收益线；问消费构成，也不默认上日历。模板库首版包含day_cards、month_grid、grouped_bar、time_line/step_line、category_bar、donut；只有后端声明满足数据条件的模板才可选择。默认一份回复一个主图，日历内联详情属于主图的选中状态，不再叠加多张完整报表。

逐日小卡建议高度约92–112px，日期与星期清楚、主金额最多一项、次要收支最多一行、事项图标和数量可点击。月份格建议约56–72px，不逐格重复免责声明；大字号和窄屏按可读性调整。可计算盈亏保留既有盈利/亏损颜色、正负号与图例；未知用断点/纹理或“—”，真零用中性样式。来源覆盖不完整时不能以“无事项”或空白格暗示无支出。

### 9.3 各模板的语义与图文对应

- 柱图：同期间、同口径的流入/流出、分类金额或期间损益；零基线明确，正负值分别表示。收入、退款、借款本金、内部转账及投资交易按现有分类合同处理，不都称收入。
- 折线/阶梯线：真实日期或日终时点作横轴；余额/权益是存量，区间损益及累计值分别命名。未来确认事项、候选情景用不同线型和明确标签，不把候选画成已发生。只在金额未变且来源覆盖确认时由后端进行日终值延续，不由前端补未知日。
- 条形/环形：环形只用于非负且分母明确的构成，类别宜不超过5；有负值、退款影响、覆盖不足或类别多时优先条形图。占比、排序和“其余”合计由后端计算并发行；不能把收入和支出硬放在一个饼图里比较。
- 缺口：折线在缺失处断开，保留缺失时间段，不能删掉空值后连接；横轴使用真实时间间距，不将间隔不等的净值点等距摆成每日曲线。
- 收益：现有daily_pnl可能是跨周末等多日净值区间的损益，interval_days/opening_on必须保留；不能平均摊成每天收益。跨月、费用、分红、拆分及所有者进出按现有方法核验，持仓累计浮盈不当月收益。
- 数据范围：币种分别展示；模拟银行、导入流水、历史研究组合和未来推演不混合。相对时间由正确业务/来源时钟解析，图标题给实际日期，不把合成账本业务日改成现实今天。

结论放在图上方一两句；关键转折可以用短注释并绑定相应日期或期间证据，不下没有依据的因果判断。底部只保留短范围/来源及查看口径入口。前端可计算柱高、线坐标、刻度与命中区域等绘图几何；轴刻度不是新的用户金额结论，悬浮提示、表格和摘要中的真实数值必须来自后端证据，前端不计算新的财务指标。

### 9.4 深层交互：围绕同一份数据继续分析

首版落实以下交互，减少常驻按钮：

1. 点日卡、柱子、折线点或分类，展示该点的紧凑明细；移动端点按完成桌面悬浮功能，键盘也能逐点选择。
2. 年→月→日→事项逐级钻取，保留面包屑和返回位置。筛选默认继承，必须明确“当前筛选”与“当日全部事项”，不能偷换图点与详情的范围。
3. 选中日期/类别后出现“问这一项”；传递受信图点引用、实际期间、来源、币种、组合和版本，让Navren回答同一对象，不只发送“为什么这么高”。
4. 允许框选时间段或选择起止日，由后端重算所选范围；图上高亮选区，局部摘要与建议问题跟随新子视图。没有新金融结论的选中/高亮不调用模型，用户要求解释时再发对话请求。

有数据及合同后再启用同口径期间对比和只读情景对照。例如原确认事项与“若已识别候选续费发生”虚线对照，或者用户明确提出“若不保留这笔额外计划预算”。原结果和情景结果分开，显示改变的条件；不修改真实账本、正式义务、预留或事件，也不把切换情景当取消订阅。参数变更必须调用后端情景计算，不能拖动图点直接更改金融数值；实际业务仍走准备与本人确认。

筛选和钻取产生绑定父快照的新子视图，原正文仍是其批准时的结论，不能只换图而让旧结论看似适用新范围。数据漂移明确提示重新查询；历史回看与当前详情分开，过期或撤回对象不从本地HTML复活。展开、刷新、语言切换和切账号都保持前节消息状态规则。

### 9.5 序列合同与金额门

Base扩展现有指标/组件体系的受控series/presentation合同，不另建平行注册表。至少包含：schema_version、presentation/view/parent引用、request/workspace与授权绑定、来源/币种/组合/核算口径、实际range/granularity/timezone/clock_basis、series_kind、x日期或期间、各值对应的指标与input_refs/source_versions、coverage/missing/interval及允许的只读交互。

现financial_metrics工具白名单和正文amount_contract并未自动覆盖calendar_query/day/budget_scenario/wealth_product中的每个值；因此现有组件可显示金额不等于新图表已经进入完整金额门。需要按原owner同时补工具提供、出站净化、最终审核投影、逐点校验、版本/授权回查、历史持久化及文字/语音最终发布，禁止用“数值画成图”豁免校验。

首版控制正文、面板、重复金额、图点及可交互值的完整声明数量，沿用24条上限；默认一条月度序列最多12个点加少量汇总，短期日卡按合法数量分页。不能靠隐藏数值标签或把金额塞进tooltip绕过限制。完整月历和较长多序列须在单独版本化series合同逐点确定性验证、同一审核投影及预算验收后启用；合同未闭合时保持可用的短窗口/聚合展示，不降低既有门。图表变成纯服务器生成也不自动免除同轮审核与最终源回查。

Agent选择合格模板及已发行引用，不输出任意JavaScript/HTML、自由ECharts配置或自编series数组。跟进问题、标题、图例、比较标签和条件都进入同一审核对象；纯布局/选中在前端做，新增摘要金额或情景回后端算。沿用紧凑来源表、完整签名和原双模型预算；不能以模板更多为由增加每次请求的润色/推荐问题模型调用。

## 10. 日历图文增量的分工与验收

- UI：先复用CalendarUI与现有统一任务组件，做聊天紧凑日卡、月历、图表模板和选中/钻取状态；让资金时间轴不再使用长折叠列表。修聊天布局、建议问题和消息恢复时保留正在做的浅色/深色主题改动。view_context.py/js/view_context.js的图点引用由其当前登记持有者完成，不能由Base抢占。
- 基座：提供日卡与月/年聚合序列、日终资金曲线、覆盖和状态、权威来源发行及子视图/明细核验。复用已完成的资金与A/B/C适配；正在冻结的联合候选不改，新合同在隔离候选推进。实际服务文件已交接时再登记精确范围，不凭旧职责表接管。
- Agent构建：按问题选择模板，同轮短正文与数据解释，保存图点上下文，完整证据审核；保持最新紧凑协议、原S10指标及预算补丁，不另写第二套链。
- 金融方法与计算：按Base接口缺口提供纯月年聚合/构成/期间收益输入合同与独立预期；只补必要的方法，不从缺份额/边界数据造曲线。
- RAG构建：仅在真实行情或产品证据覆盖缺项时交现有来源与缺口清单；此次不要求重新采集多年全量数据或改已封存最终发布守卫。
- 集成验收：保留当前冻结G1及原金融题；新合同稳定交接后独立验证消息组件、周期聚合、同一来源的钻取/筛选与所有交互状态，不把模拟组件测试等同真实用户链。

新增验收：一日/一周/月/半年/一年/十年请求模板与来源正确；实际事件点击可读全部分页明细；候选/确认、已知零/未知、跨日收益与缺失断点正确；正负类别拒绝环图；币种/份额/时钟不混；图表金额/比例篡改、选点改对象、跨账号重放和版本漂移被拒；区间筛选后文本/摘要/建议与子视图一致；月历与轴标签不超出消息列；普通/深色、窄屏、键盘、触控、中英和放大字号可用。交互只读不会新增操作、预留或正式记忆。
