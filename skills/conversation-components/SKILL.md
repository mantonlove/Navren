给出紧凑、可扫读的完整回复：短句说明结论，少量加粗突出决定判断的信息，成组关系交给合适的组件。组件只负责表达，不是可信来源、计算能力或操作授权。

## 先形成这次要交付的回复

当用户要“简洁比较、怎么选”且几个维度都会改变取舍时，先给一句带条件的判断，再用一份 `navren-compare` 并列关键差异。不要把每个方案分别扩成长段，再追加“所以”和“一句话”重复总结；只有一个差异或用户明确只要一句话时，直接短句回答。这里的受限组件围栏由客户端渲染，不是要求避免的普通 Markdown 表格。

自由正文中的关键数字、日期和决定取舍的条款，用 `**关键词及必要限定**` 做语义加粗；保持其余文字正常。只有重点没有次要信息可区分时，不必硬加粗。交稿时从用户可见回复检查是否实际做到，而不是只在内部判断过。

一份完成稿的形态（下面只示意表达，必须替换为本轮事实）：

````text
更看重**可自主安排时间**时偏向方案乙；必须**现场交流**时偏向方案甲。

```navren-compare
维度 | 方案甲 | 方案乙
时间 | 固定时段 | 自主安排
交流 | 现场交流 | 异步反馈
```
````

对比里的内容不再逐方案复述，也不在末尾重写一次同义结论。需要解释某项取舍时，只补该项必要条件。

只说本轮材料支持的条件。“提前两天可取消”不足以断言临近时点完全没有其他安排；退款未知就保留未知。解释限定为何影响选择即可，不补写未给出的失败后果或反复做风险推演。

## 先判断阅读任务

先在内部辨明用户要理解原因、核对条件、比较选择，还是按顺序做事；再找出真正改变答案的信息关系。不要向用户输出这份内部判断过程。

从材料中先提炼判断骨架：用户现在要决定什么；哪些条件会改变结论；哪些只是解释或背景。宣传词、重复介绍与无关属性不因为原文里有就进入组件。同一份材料在不同目标下应选择不同的重点；用户改了目标，重新判断资格、期限和取舍，不只改表格标题。

| 这次阅读需要 | 选择与取舍 |
| --- | --- |
| 一两句话就能说清、随口交流，或只缺一个关键条件 | 普通文字，可少量加粗关键值与条件，或作一个简短澄清。缺资料不画一排“待提供”卡片。用户要求一句话、纯文字时优先照办。 |
| 成组详情确需反复扫读、本条勾选核对或按需展开答案 | `navren-panel`：正文说明重点，面板承接确有阅读或交互收益的详情。几个数字、少量时间点能直接说清时，用正文或紧凑列表；不因有数据就加面板。 |
| 同一问题下有几项需要一起核对的事实、条件或判断 | `navren-facts`，各行共享一个对象或判断任务；一条因果解释仍用段落，不拆成“原因/影响/结论”伪要点。 |
| 两三个选择需要沿相同维度看差异 | `navren-compare`，把选择放列、判断维度放行。先统一口径；资料不对称时保留缺口，不能造值凑齐。 |
| 方法或过程确实有先后依赖 | `navren-steps`。并列建议、独立事项的优先级用列表或要点，不用编号制造依赖；步骤只说明方法，不冒充办理进度。 |
| 有一条需要与主体分开的适用边界 | `navren-note`。影响结论的条件须紧邻相应内容，不能都藏在末尾旁注。普通补充直接写一句。 |
| 已有金融事实、趋势、资金拆解或日历 | 加载相应领域技能，沿其事实投影或真实 `widget_ids` 展示；不把已存在的金额、图表和事件再复制成自由组件。 |
| 需要用户选择、授权或确认操作 | 沿当前 `interaction` 或业务原生确认卡。轻组件只读，不能生成替代按钮、表单或执行能力。 |

先把同样的信息想成一段正文或一个紧凑列表：若组件只增加外壳、标题、摘要、滚动和展开动作，没有更便于核对关系，就保留文字。密度是必要判断信息与阅读负担的关系，不靠缩字、堆满或删掉条件提高。

任务可能只有文字，也可能是文字与一种组件配合。不必凑齐类型，不追求每轮都换花样。当前注册结构不能恰当地表达时，用段落、普通列表或已有原生组件，不自造组件名、HTML 或客户端尚不支持的布局。

## 保留决定判断的信息关系

让事实始终带着其对象和适用条件。“同时满足”“任选其一”“仅限”“除非”决定能否成立，压缩时不能丢。已知硬条件不满足时先指出；仍缺关键条件时保留未定，不能把“没发现冲突”写成“符合”。需要同时核对资格和时间时，各自保留，不用一个笼统的“可用”合并。

多份记录先核对象、适用范围和事件时间；同口径确有分歧时展示分歧及其影响，不悄悄选一个值，也不以最新转述自动覆盖已有证据。计划、提交、测试通过、部署和用户实际可用各自依原材料保留；不同对象的事件不能串成一条共同进度。没有总节点及完成证据，不产生完成率或成功色标。

复杂材料怎样提炼、混合关系怎样落进现有结构，见 [编排与取舍](references/composition.md)。需要时再读，不把内部整理表作为额外输出。

## 编排一份完整回答

先直接回答用户最关心的结论，再把需要扫读或交叉核对的内容放进组件。正文承担解释、因果与取舍，组件承担成组事实、差异或顺序；不要在前后再逐项复述同一内容。若结论本身是条件性的，第一句就保留条件。

在普通正文中，用少量 `**加粗**` 标出关键数字、决定取舍的差异和会改变结论的条件。数字连同单位与必要范围一起强调，例如“已读 **60%**，剩余资料尚未核对”；不能把“预计”“仅限”等限定留成不显眼的附注，让强调后的片段变成另一种结论。不要整段加粗，也不把每个名词都当重点。受控金额和原生业务片段仍按原合同展示。

组件是可选表达；需要时一组通常足够。只有用户确实有两个独立阅读任务时才用第二组，单条回答最多两组。已有业务图表或确认卡也占据阅读空间，优先让正文承接解释，别在旁边再堆同内容的轻组件。

每组只留影响判断的信息，不凑项数，硬上限不是建议填满的数量。标题只有能指明分组对象时才写；已由正文交代的主题，不再用标题、摘要和块标题重复三遍。可省略的 summary、块标题和说明，没有新增信息就省略。标签用可快速辨认的名词，值直接回答标签，说明只补必需限定。不要用多个同义行或空字段撑大组件。

对比按最影响取舍的维度排序，每个维度提供不同的判断信息，同一属性不要换标签重复一行。单元格保持短而可比；长原因移到对应表后解释，并明确所指对象。不能删掉锁定期、适用资格等关键条件来压缩。内容无法简洁放入时，减少非必要维度，或改为分对象短段落；不能靠缩字、截断或制造更多嵌套卡片塞满。窄屏由客户端重排，不以桌面横向表格为唯一读法。

追问只承接当前新增问题：用户只问其中一项，就解释这一项；要求展开才补相关内容，不机械重发整张表。用户纠正条件时更新受影响的比较和结论，保留原不确定性，不把上一轮方案写成已选或已执行。

字级、颜色、尺寸、图标和边界由客户端统一控制，继承当前主题和用户字号。正文的加粗用于语义强调；组件字段继续按协议写纯文本，利用既有标签、值和条件位置承载重点，不在字段内塞 Markdown 或新增 emphasis 等字段。不要输出样式指令、巨型数字、装饰性状态或额外卡壳；信息关系和文字轻重应先于外观装饰。更多内容编排例子见 [编排与取舍](references/composition.md)，只在需要复杂对比、追问或长内容时读取。

## Aura 面板的 Navren 适配

参考 Aura 的面板积木能力，是否使用仍由本次内容决定。先看正文加粗、短列表或原有轻组件能否说清；只有确需成组详情或本地阅读交互时才使用面板。使用时正文说清结论及会改变判断的限制，面板承接其余详情，不在两处重复。不要把关键资格、风险或未知藏到折叠后才说。选择足够表达关系的最少结构，不为展示能力拼指标、进度和时间线；硬上限三块，只围绕同一阅读任务。

- 需并列扫读的少量非金融数值用 `metrics`；需要按时间定位的节点用 `timeline`，不要把计划画成已发生。
- `progress` 仅展示本轮明确提供的百分比；`bars` 仅对照同口径非金融数值。未知不填零，不从进度推出完成或收益，不以图形替代原生金融事实组件。
- `checklist` 是本条面板中的阅读核对，勾选不保存业务任务、不开启授权或确认金融操作；`quiz` 只在用户需要自测时使用，展开答案不代表学习完成。
- 文件入口、追问和办理按钮沿 Navren 原有工具与交互。此适配不生成 `a-file`、`a-ask`、任意 HTML、代码、URL 或可执行参数，不引入 Aura 的账户、服务端工具或 React 运行环境。

基本语法随本技能即可使用，无需为查格式额外读取；示例不代表这些少量信息应当做成面板：

````text
```navren-panel
{"title":"资料安排","summary":"已有内容和后续节点","blocks":[{"type":"metrics","items":[{"label":"已整理","value":"4","unit":"份"}]},{"type":"timeline","items":[{"at":"周五","title":"核对材料","detail":"这是待办安排，尚未办理。"}]}]}
```
````

这是格式示例，不是用户事实。blocks 每项有 type 和可选 title，字段按类型选择：text 用 text；metrics 用 items[{label,value,unit?,note?}]，value 是文字；timeline 用 items[{at,title,detail?}]；checklist 用 items[{text,detail?,due?}]；progress 用 items[{label,value,note?}]，value 是0至100的已知百分比；bars 用 unit?、items[{label,value}]，value 是0至1e9的已知非负数；quiz 用 items[{question,answer}]。问号表示该字段可省略，不输出问号键。每块最多六项，metrics 最多三项、quiz 最多五项；text 最多600字。面板 title≤40、summary≤120，整段 JSON≤6000字，不加其他字段。

组合较长内容或需查完整字段上限时再读 [面板协议](references/aura-panels.md)。它与已有轻组件共用已审核正文、收藏和朗读；不新增终结字段。每次最多一张面板，当前 schema 的自由正文限制仍适用。没有必要详情就不用面板，已有金融图表及确认卡不再抄一遍。

## 使用当前客户端支持的结构

先看本轮实际终结 schema。只有允许自由 `text` 的通道才可用以下围栏，并通过原终结工具提交。需要组件时宜在资料读取与内容组织阶段加载本技能；进入只准提交终稿或修稿的阶段后，不为排版增加读取或模型轮次，按已知格式输出或退回文字。

最小语法在这里即可使用，无需另读参考：

````text
```navren-facts 可省略的标题
标签 | 值 | 可省略的说明
另一标签 | 另一值
```
```navren-compare 可省略的标题
维度 | 选项甲 | 选项乙
比较维度 | 甲的情况 | 乙的情况
```
```navren-steps 可省略的标题
步骤名 | 本步说明
下一步 | 下一步说明
```
```navren-note 可省略的标题
一条需要独立说明的条件。
```
````

示例只表示语法，不是用户事实，也不是建议每次输出四块。内容均为纯文本，不在单元格里嵌套 Markdown、管道分隔符或围栏。每块总长最多2400字；要点和步骤最多六行，对比最多六个数据行、2至4列且列数一致；旁注最多400字；标题最多40字。写短而完整的内容；具体字段上限及格式回退见 [组件协议](references/component-format.md)，接近容量限制时读取。

若当前是 `reply_parts`、`direct_answer`、受控费用/时间、严格历史引文或纯 `answer_facts` 模式，沿其原合同输出，不新增字段或围栏，也不为展示扩大查询。不能把部分围栏跨多个 text / metric 片段拼接，或为获得自由正文而切换终结模式。金融签名、事实资格和业务交互优先于这份展示方法。

## 证据与发布

组件里的每个字仍属于同一份待审正文，继续经过原隐私、金额、来源、完整审核与发布检查。公开事实引用本轮来源，用户假设与本人账户事实分开。不可把新闻数值当本人余额，也不可因组件名含 facts 添加“已核验”“实时”“已执行”等资格。

不在轻组件中生成按钮、确认、交易动作、表单、URL、代码执行或授权参数；来源引用和原文入口沿原回复合同承接。需要用户澄清沿现有 `interaction`；金融、日历和记忆授权沿各自真实确认卡。任何只读展示都不能代替这些卡片。

提交前按成稿读回，而不只核格式：用户能否据此知道结论在什么条件下成立、什么变化会使它改变；单独看表中一行，是否仍能认清对象、时间及必要限制。若压缩后会作出错误判断，先恢复条件、重组或退回短段落，不另加一张解释卡补洞。再检查正文与组件是否重复、追问是否只补所问，以及当前 schema 和客户端是否支持。组件没带来阅读收益时，删去结构、保留完整文字。不把格式合法或成功渲染当作内容正确、设计已获认可或真实模型效果已通过。
